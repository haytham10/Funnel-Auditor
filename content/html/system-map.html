The run, end to end

skill: outbound-batch

Every stage below is expandable. The rail is neutral where the machine spends nothing and marked where money can enter — which is one stretch, and it is fenced by a cost gate at both ends of it.

01intake

Raw list → Leads

detail

GuaranteesJunk and parked domains classified, not silently dropped. Platform URLs routed to their social columns. Unmapped headers reported.

The platform verdict is the one the old pipeline got wrong. A LinkedIn URL in the website column is not a dead end, it is the best research target on the row. On the last real list, 24 of 137 "websites" were not websites, and 199 of 336 rows had a dead or missing site — so a hard site gate was throwing away most of the market.

02dedupe
early

The wall, before anything is spent

detail
free exit 1 — warm hit stops the run exit 2 — unreadable or empty
python main.py dedupe work/leads.json --out work/clear.json
Matches onName and domain. Exact on domains; two-tiered on names — strict key in reading order, loose key sorted.
Readsdata/contacted-before.csv, in the repo. No fetch, no argument.

This ordering is the bug the old pipeline shipped. Dedupe ran last, so an already-excluded lead paid for all eight Apify calls and was then thrown away. A text match costs nothing and belongs first. On the last real batch it caught 7 people who would have received a cold template on an existing thread, two of them live warm conversations.

An empty wall exits 2, not 0. A missing file is indistinguishable from a broken one, and guessing costs a live conversation. A loose-only name match stops the run against a warm contact and merely reports against a cold one — a false kill is permanent and invisible, a second cold email months later is not.

04fetch

The ladder: free first

detail
tier 0 · 1 tier 2 · batched
python main.py fetch work/clear.json --out work/sites.json --with-text
tier 0local requests + BeautifulSoup — free
tier 1the agent's own WebSearch / WebFetch — free, model-side
tier 2one batched Apify cheerio run — paid, shared

Container boot dominates the bill, not pages. A 2-page run and a 200-page run cost nearly the same to start, so tier 2 never fires per lead — it fires once per batch, over every URL tier 0 failed on. Fifty separate two-page runs is the worst possible way to use a compute-billed actor.

Two traps this module is shaped around. Called without setting crawlerType, the actor defaults to full headless Firefox — one test run spent 81 seconds on 2 pages and 45% of that lead's entire bill. And depth-2 crawling missed /about.html on a real lead, so candidate URLs are enumerated directly rather than discovered.

Firecrawl is gone as of 2026-07-31. The tier-0 read rate is unmeasured — the first real batch measures it, and every cost estimate downstream depends on it.

05research

Workers → typed objects → schema

detail
research-worker ×n schema, not a verifier exit 1 on a clear no
python main.py research work/research-<slice>.json python main.py qualify <lead.json>
Fan-outOne worker per slice of ~10 leads, at most 5 at a time. Workers write nothing — they return typed objects.
The three floorsUAE-based (based here, not merely serving here) · actually a coach · active in the last 30 days
Captured, never gated oncoach_type sells_to audience_size top_program_price_aed solo

unclear passes. Only a clear no drops a row. A false kill is permanent and invisible; a false pass costs one research call. Every verdict carries the source that settled it, so a no can be argued with instead of taken on trust.

A verdict without a source is not a verdict. The schema rejects any hard yes/no naming nothing — that combination means the answer was reasoned rather than fetched. This is the one stage with no verifier agent, on purpose: a schema check is cheaper than an agent and strictly harder to talk around.

Two floors were removed and both were wrong differently. Audience size decoupled from the offer the moment we started selling their next client rather than leverage on their list. And a price floor reads unclear on ~94% of the market — a coin flip with extra fetches attached. coach_type still matters because it picks the identity line, and LinkedIn wins when the site disagrees.

then, now that addresses exist

python main.py dedupe work/researched.json --stage late

Pass 2 runs on email. Pass 1 cannot catch a married name, a business name that doesn't resemble a person name, or an address that only matches once you know it. Both passes are needed; neither is sufficient.

the address itself

python main.py email-check # free: syntax, MX, role/typo flags python main.py email-verify # paid deliverability confirm python main.py email-enrich # no-address fallback, own branded domain

The fallback converges on exactly one address, never auto-passes a catch-all domain, and refuses free provider domains. Verification defaults to Apify/MillionVerifier and auto-falls back to ZeroBounce when Apify is near cap.

06hook

Proposed, then re-fetched cold

detail
hook-worker hook-verifier defaults to refuted
Worker proposesThe exact quote, the URL and the date. It never writes the hook anywhere.
Verifier confirmsRe-fetches the citation in a context that never saw the search, and confirms the quote, the date and the authorship actually hold.
Three verdictsverified refuted inconclusive

Never invent a hook. It is a citation or it is nothing. No hook found is a good answer — the lead holds and gets no row. INCONCLUSIVE (page gone, login wall, content changed) holds the lead where it is rather than killing it, and a refutation needs a citable contradiction, never a feeling.

Do not summarise the worker's reasoning into the verifier's prompt. That destroys the entire mechanism while looking helpful. Hooks are pipelined: one can be verified while others are still being found.

Quality tripwire. If the verifier refutes two or more of the first wave, stop and surface it before spending the rest of the queue. Two refusals in a row is a problem with the instructions, not with those two leads.

The verified hook's date is the activity evidence — write it back. The 30-day floor runs at research against a site read, and a coach's own website almost never carries a date: measured across nine real sites and ~220,000 characters, zero usable ones. So every lead came back unclear and the floor did nothing. LinkedIn is where the signal is, and this stage is what fetches it.

07deal

Which hand-written lines this batch gets

detail
copy-check: pass / fail / blocked deal exits 1 on a rejected live edit
python main.py copy-check python main.py deal work/draftable.json --out work/anchors.json

Airtable's Copy Assets table owns every line. copy/*.csv is a cache of it, not a second opinion. copy-check asserts both halves: the live lines pass the linter, and the committed cache still matches them. It only looks — it is the reader to copy-sync's writer, so it is safe at the top of a batch and again after a fix.

A batch is dealt, not rolled. Per-lead hashing is unbiased only in the limit: measured on the live lines, a 50-lead batch gave one offer line 8% against a declared 20% and pushed another over the repetition cap. It converged near n=200, and batches are not that big. Dealing gets the worst miss to about a point. anchors keeps the per-lead draw for single-lead work.

The repetition cap outranks the 70/30 exact-match ratio. When a segment has too few identity lines to spread its share, the excess spills to generic rather than putting one sentence in front of 70% of a batch. deal then prints a THIN line naming the segment and how many more lines it needs. That is the fix; the spill is the workaround.

Every rung below the live one records why it was taken, printed as a COPY: line. All three failures — a dead key, an unreachable base, and an edit that fails the linter — used to be swallowed into the same silent fall-through, so a batch could ship on month-old copy while the operator believed the table was in charge. --allow-cached-copy is the one deliberate override.

08draft

Written against the anchors, then read cold

detail
draft-worker draft-verifier send / rewrite / reject
Worker getsThe verified hook, the research object, and that lead's four dealt lines, inline in the prompt. It runs the linter on its own output before returning.
Verifier judgesThe one thing no linter can check: whether beat 1 connects to beat 2, and whether it still sounds like me. It never edits the draft.

The model may re-voice an anchor so the beats connect. It may not change what the anchor claims. That single sentence is the whole arrangement — it buys real freedom for the drafter while keeping every claim traceable to a line a person wrote and checked.

The worker must not draw its own lines. It would get the single-lead draw rather than the dealt one, which breaks the balancing and leaves the CRM record disagreeing with the email that shipped.

sendinto the export set
rewriteback to the drafter once, with the note. Then it passes or it holds.
rejectholds. No row.
09lint

Everything that can be mechanical

detail
fails closed exit 1 on any draft or batch failure
python main.py lint <drafts.json>
TraceabilityEvery number must be true of a real client result in copy/results.csv — and a number next to a named segment must belong to that segment. Invention and relabelling are two different failures, and either is the tell that the whole email is fabricated, hook included.
Claim preservationThe offer beat must still offer ten names. The close must still ask for fifteen minutes and keep its second half. A close that loses its reason becomes a question, and that is how reply-to-call went 0-for-9.
VoiceNo em-dashes. No operator jargon. No weak closers. Signs off Haytham. Second person before the first digit. No gendered pronoun in an identity line.
Batch-level67–95 words · no fixed line above 35% of the batch · bridge phrases capped at 10% · share checks from 8 leads up. Invisible one email at a time, which is why they run across the file.

Jargon is matched on word boundaries, with explicit suffixes. A raw substring test dropped real emails and gave a false reason: the hook quotes the lead's own words, so "optimism" tripped optimi, "auditioning" tripped audit, and "Detroit" tripped ROI. Each rejected a whole email naming a word that was never in it — unfixable by the drafter, because the complaint is not true.

Five files, and the one you have to read

detail
a failed lint is absent, not flagged --anchors checks id and text
python main.py export work/drafts.json --anchors work/anchors.json \ --out out/ --batch <YYYY-MM-DD> [--rebalance-ps]
out/leads.csvExactly eight columns. Smartlead stitches nothing — what you read in the preview is byte-for-byte what leaves.
out/preview.txtThe gate. Every email in full, in order.
out/rejected.txtEvery lead that did not make the file, with its reasons.
out/wall-additions.csvHeld back deliberately until after the upload.
out/line-usage.csvSame — what shipped, for Copy Assets.
email, first_name, last_name, website, linkedin_profile, location, subject, body

It is linkedin_profile, not linkedin_url. The wrong spelling still imports successfully and silently lands as an extra custom variable, which is the worst kind of wrong. Six columns are Smartlead's native fields; subject and body arrive as custom fields used as template variables in a campaign step.

Export against the same deal file the drafts were written from. Re-running deal after drafting produces a different allocation, and --anchors then compares each draft against lines it was never given — the rejection reads "the drafter drew its own", which is the opposite of what happened.

--rebalance-ps whenever any lead held. Holds are guaranteed, and every hold unbalances a deal made for the larger batch: dropping 3 of 11 on the first real run put two ps lines at 38% against a 35% cap and correctly blocked the whole file. The ps is the one beat that can move safely — library copy, near-verbatim, alone at the end, no part in the seam. Re-dealing from scratch would move identity lines and force re-drafting emails that already passed a cold read.

All five outputs are cleared first, so a blocked batch cannot leave a stale uploadable file behind.

11after
upload

Only once it has actually been sent

detail
wall-add is idempotent copy-usage is not — run once
python main.py wall-add out/wall-additions.csv python main.py copy-usage out/line-usage.csv git commit data/contacted-before.csv

Nothing was sent at export time. Walling a lead who never received anything would silently exclude them from every future batch. copy-usage adds to a running total and nothing can tell a re-run from a genuine second batch using the same lines, so it runs exactly once — --dry-run first if unsure.

The batch is also written to Airtable: one Batches row and one Leads row per lead including the ones that held, with their blockers. A lead that vanished with no record is worse than a kill you can read.

The one instruction no code replaces

Read out/preview.txt before uploading. Ten emails, in full. The linter catches invented numbers, lost claims, jargon and repetition. It cannot catch a hook that lands wrong on a specific person, or a paragraph that passes every rule and still reads like a robot. That has always been the gate and it still is.

The gates, and what a code means

Universal across every command and pinned by tests/test_cli_failures.py. Skills quote the literal output line rather than paraphrasing it, which only works if the codes mean the same thing everywhere.

0passThe check ran and passed.
1failThe check ran and something failed.
2could not runThe one that matters. A check that cannot run is a failure, never a pass.
3needs approvalA paid call above the cost ceiling. It blocks rather than spending.

A missing wall file must never read as "nobody has been contacted". A missing docs tree must never read as "no drift". Every gate fails closed.

04

What one email is

67–95 wordsplain text no links · no price

Each beat answers the objection the reader raises at that exact moment. Reorder them and a beat answers a question the reader has not asked yet, which reads as a non sequitur even when every sentence is individually fine.

1

Hook

is this a spammer?

One or two sentences about something specific and recent they did, cited, plus a clause saying what you took from it. The only beat written from scratch, and the only one an independent agent re-fetches.

written per lead · owned by docs/hook-rules.md
2

Identity

who is this and why should I care?

A matched reference group, a real number, a timeframe. It must turn to the reader before its first digit. An identity beat that opens on my numbers is a CV; the same numbers after "your next client is the job" are evidence.

anchor · 33 lines · matched on coach_type AND sells_to
3

Offer

what can you do for me?

Ten names, already pulled. Not a promise to pull them.

anchor · 4 lines
4

Close

what happens next?

Fifteen minutes, a clock on the deliverable, and why these ten and not the other forty. The close must keep its second half. A close that loses the reason only a conversation can answer becomes a question, and a question selects for replies that are answers — a dead end that looks like success.

anchor · 4 lines
5

ps

what does saying no cost me?

A costless no. Not a throwaway — it is the beat that makes not replying cheap, which is what makes replying honest.

anchor · 4 lines · the only beat --rebalance-ps may move

The bridge

The single most common failure, and the one that cannot be repaired downstream. The hook must have a writer in it.

"You wrote that you couldn't contain the excitement of uncovering a solution for yourself." — hands them back their own sentence and stops.

"…That is a strange thing to read from someone who sells the solving." — has a person in it, and beat 2 now has somewhere to start from.

A hook with no writer produces an identity beat that reads as a non sequitur whatever that beat says, which is why no amount of rewriting beat 2 fixes it.

What is sold

Ten names. Real people who fit their buyer profile, already pulled, handed over on a fifteen-minute call along with why those ten and not the other forty. That is the entire ask.

No price appears in any email. The paid offer lives on the call. Nothing in the machine quotes a number, and doc-check enforces that docs/spec/03-offer.md is the only defining doc allowed to carry one.

The previous system sold a finding — and a finding in an inbox is a free fix. 4 of 9 engaged leads read it, fixed it themselves and left. 589 leads, 0 calls, at a reply rate of 7–9% against a 1–5% benchmark.

05

The worker / verifier chassis

The agent that makes a consequential claim never gets to certify it. A second agent, which never saw how the claim was reached, re-derives it from the evidence alone and defaults to rejecting it. The fix is structural, not motivational: a third of self-certified findings used to fail under scrutiny while carrying a verified flag.

Research

research-workerResearches a slice of ~10 leads into typed objects. Spends the cheapest tool that settles each datum.
no verifier — on purposeA schema check is cheaper than an agent and strictly harder to talk around.
the checkpython main.py research rejects a verdict outside the enum and any hard yes/no with no source.

Hook

hook-workerProposes with the exact quote, URL and date. Never writes the hook anywhere.
hook-verifierRe-fetches the citation in a context that never saw the search. Defaults to refuted.
the one claim re-checkedThe quote is really at the cited URL.

Draft

draft-workerWrites one email from the hook, the research object and the four dealt lines. Lints its own output.
draft-verifierReads the finished email as its recipient would. Never edits it.
the one claim re-checkedBeat 1 connects to beat 2, and it still sounds like me.

The rules that make it work

  • The verifier never sees the worker's reasoning. Summarising the search into its prompt destroys the mechanism while looking helpful.
  • Three verdicts, not two. Inconclusive holds the lead. A false kill is permanent and invisible.
  • Only the verifier promotes. The worker proposes; the flag is written by the thing that checked it.
  • Cross-check the store, not the report. A claimed success over an unwritten row is Blocked, not Done.
  • Prefer a mechanical check to an agent, always. The linter, the research schema, the wall and export --anchors each replaced something a person or an agent was supposed to remember.
  • Least privilege. No worker gets a send-capable tool. No worker spawns sub-workers.

Who orchestrates

The skill is the orchestrator, running in the main loop. It does three things and no per-lead work: fetch a batch, fan out, write the result. The exception is a stalled worker, taken over directly rather than nudged twice.

outbound-batch A whole list, end to end, into a file.
outbound-draft One email, and the repair path. Carries the voice references.

The repo's .claude/skills/ is authoritative — a SessionStart hook fingerprints every on-disk SKILL.md, and if a remembered copy disagrees, the file on disk wins.

Why the lines are in Airtable and the results are not

They look like the same kind of thing and they are not. The lines are voice — tweaked, reworded and retired, often several in a sitting, and Airtable is a much better place to do that than a CSV. copy-sync is what makes it safe.

The results are evidence. Eight hand-filled intake forms, and the thing every number in every email traces back to. They should not be casually editable, so they are not in a tool that makes editing easy.

Why one row needs a live check

Every other authority is in this repo, so the rule is enough: a change is a commit that shows up in a diff. The CRM's select options are edited in a browser by someone not thinking about this repo, they have no diff, and three modules mirror them — a mirror of a schema nobody here owns goes stale silently, and pointing at the authority does not fix it, because the pointer cannot tell you it moved.

Outside the repo

Four services, and the two places a check runs without being asked.

Airtable crm + copy

Base appejF07kunksqt4D. Leads, Batches, Copy Assets. Owns every hand-written line and where each lead is right now.

Reading from Python needs AIRTABLE_API_KEY. anchors.py tries live, then the last synced snapshot, then the CSVs — and caches for the process, because a 200-lead batch made 200 identical requests and would trip the rate limit.

The old funnel-audit base is archive only, never written to.

Apify the only paid layer

No-login third-party fetch for what is genuinely login-walled. Needs APIFY_TOKEN. Cost-gated at $0.10 per run, exit 3 above it.

Check the budget once per batch. Batch every URL into one run — container boot dominates the bill, not pages.

Email verification

Apify / MillionVerifier by default, auto-falling back to ZeroBounce (ZEROBOUNCE_API_KEY) when Apify is near cap.

Force with EMAIL_VERIFY_PROVIDER=zerobounce.

Smartlead owns sending

Inboxes, warmup, the ramp, the sequence steps and the replies. No API key here. Handover is a CSV I upload by hand.

Follow-ups — touches two and three — are Smartlead sequence steps, and nobody has decided whether they should be personalised per lead.

The push hook

.claude/hooks/schema_drift.py fires on every Bash call, returns immediately unless the command contains git push, then compares the select mirrors against the live base.

Drift blocks the push; a failure to reach Airtable warns and allows it. Opposite defaults, because a stale mirror endangers a batch rather than a merge, and an outage must not hold every unrelated push hostage. It exists because CI has no key and this is where one lives.

CI

doc-check and the full suite on every push and pull request.

doc-check gets its own named step even though the suite covers it, so a docs drift reports as a failing step printing its own line rather than a pytest traceback somebody has to read. It runs without --live — CI holds no CRM credential, and nobody has decided whether it should.

The two rules only a person can keep

✕Never send an email. The machine ends at a file. Sending is Smartlead, and I am the one who triggers it.
✕Never log in to, act as, or automate anything through my own accounts on any platform. Read-only, no-login tools only. This is an identity rule, not a platform ban: public data through a no-login third party is fine, on LinkedIn and Instagram the same as anywhere.
